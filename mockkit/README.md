# mockkit — version-aware Mockito mocks for Maximo business objects

Unit-test the logic you wrote *inside* Maximo — field validations, save
hooks, cron tasks, automation-script logic that manipulates `MboSet` and
`Mbo` — in milliseconds, with no running server, no test database, and no
IBM JARs on the build machine.

```java
MboSetLike assets = MockMboSet.of("ASSET", Lens.active())
    .row().set("ASSETNUM", "11430").set("SITEID", "BEDFORD").done()
    .build();

MboLike pump = assets.moveFirst();
pump.setValue("STATUS", "OPERATING");          // checked against the captured dictionary
pump.setValue("NOTAFIELD", "x");               // throws UnknownAttributeException — fail closed
```

## Modules and the interface seam

```
mockkit/
├── core/            IBM-free. Always builds: mvn -q -pl core verify
├── profile-mas91/   psdi-typed adapters — compiles only with libs/9.1/ JARs
├── profile-mas92/   psdi-typed adapters — compiles only with libs/9.2/ JARs
└── libs/            gitignored; see libs/README.md for extraction
```

The build **must compile without IBM JARs present**, so nothing in `core`
imports `psdi.*`. Instead, `core` defines a small seam —
`seam/MboLike`, `seam/MboSetLike`, `seam/MaximoServerLike` — mirroring the
psdi surface the kit mocks. Write (or adapt) your business logic against the
seam and it is unit-testable anywhere; the profile modules provide the
psdi-typed adapters (`PsdiAdapters.adapt(...)`) and the
`MXServerMockExtension` (one `mockStatic(MXServer.class)` per test class)
for code that must touch real IBM types.

The profile modules are activated by the presence of
`mockkit/libs/<lens>/businessobjects.jar` (Maven file-activated profiles),
so `mvn verify` with an empty `libs/` builds and tests only `core`. Adapter
signatures are compile-checked against *your* extracted JARs — a signature
IBM changed between release lines fails your build here, which is the
version bug the kit exists to surface.

## The fail-closed dictionary

Attribute access is checked against the dictionary captured for the active
lens (`-Dmaximo.dictionaries`, generated by `capture/capture.mjs`):

- an attribute the lens does not define **throws** (`UnknownAttributeException`,
  mirroring Maximo's attribute-does-not-exist error) on read and write;
- `setValue` enforces required, length, INTEGER type, and domain membership
  (when domain values are captured) from `mxobjectcfg`;
- an object the dictionary does not describe cannot be mocked at all.

A mock that returns whatever the test wants is the fastest way to a green
suite that proves nothing. This one refuses what the release line would
refuse.

## The evidence discipline: `@EvidencedOn`

Every test states the lenses its expectations are evidenced for:

```java
@Test
@EvidencedOn({"9.1", "9.2"})
void assetTypeDivergesBetweenLenses() {
    if ("9.2".equals(Lens.active().label())) {
        mbo.setValue("ASSETTYPE", "PRODUCTION");        // exists in 9.2
    } else {
        assertThrows(UnknownAttributeException.class,
            () -> mbo.setValue("ASSETTYPE", "PRODUCTION")); // not in 9.1
    }
}
```

The `EvidenceExtension` (auto-registered for the module) reads
`-Dmaximo.lens` and:

- **skips loudly** any test not evidenced for the active lens — the skip
  reason names both sides;
- **fails** any test with no `@EvidencedOn` at all.

## Running

```bash
cd mockkit
mvn -q -pl core verify                    # lens 9.1 (default), synthetic dictionaries
mvn -q -pl core -Dmaximo.lens=9.2 verify  # lens 9.2 — divergent expectations flip
mvn -q -pl core -Dmaximo.lens=9.2 \
    -Dmaximo.dictionaries=/path/to/dictionaries verify   # your captured dictionaries
```

The default dictionaries root is the committed `dictionaries/_synthetic`
samples (clearly labelled `SYNTHETIC_PLACEHOLDER`) so the kit runs out of
the box; point `-Dmaximo.dictionaries` at real capture output for evidence
that means something.
